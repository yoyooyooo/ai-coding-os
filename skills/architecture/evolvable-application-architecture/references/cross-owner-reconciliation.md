# Cross-Owner Reconciliation

Use this lens when product meaning, source architecture, frontend ownership, Effect mechanisms, and observed reality appear to disagree. It is an on-demand interpretation surface, not a separate architecture authority.

## Normalize the disagreement

For the disputed claim, state:

```text
accepted meaning
source reality
observed reality
current owner
candidate target or proposal
unknowns that can still change the decision
```

Many apparent conflicts disappear when scope or knowledge role is made explicit.

## Typical disagreements

### Product says one thing, source does another

Determine whether source drifted, product knowledge is stale, or a deliberate compatibility period is active.

### Source looks correct, runtime fails

Treat runtime as bounded evidence. Find the first wrong state before rewriting accepted architecture.

### Frontend and backend both appear authoritative

Separate user intent, optimistic proposal, server accepted fact, projection, and realtime continuity.

### Effect mechanism appears to dictate architecture

A Layer graph may assemble capabilities but does not decide product fact authority, package boundaries, or domain ownership.

### Current and target architecture are mixed

Keep current source and target decision both visible. Do not present the target diagram as current fact before migration.

## Decision review

A useful reconciliation asks:

```text
Outcome        which user or operational result is protected
Authority      who may define the disputed meaning
Reality        what source and observation actually show
Changeability  which option contains the next real change
Feedback       what observation can decide the remaining uncertainty
Containment    how failure and irreversible effects are limited
Operability    how future Agents run, inspect, and diagnose it
Responsibility who can accept the remaining risk
```

These are lenses, not a scoring system.

## Output

Return the smallest set of corrected ownership statements, source changes, documentation updates, and evidence needs. Do not create an ADIR, health score, or closure artifact unless a real external process consumes it.
