# Earned Shape and Identifiers

Structure is useful when it reduces real ambiguity or navigation cost. It becomes harmful when it creates empty authority surfaces, false maturity, or extra translation work.

## Start flat inside the correct home

A new durable subject normally begins as one file or a small coherent cluster in its owning home. Partition only after durable pressure appears.

## Directory admission

A child directory is justified when one or more are true:

```text
independent semantic owner or audience
independent security/access policy
independent retention or lifecycle
repeated edit conflicts or direct linking pressure
stable high-density lexical cluster
machine consumer or framework requirement
```

File count alone is not sufficient.

## Partition defaults

- a child directory inherits the parent Home's semantic role; it does not create a new authority layer;
- keep shared material at the Home root;
- use one primary organizational axis at each nesting level;
- asymmetric shape is healthy: only the area that earns a partition receives one;
- a child `README.md` is a local router, not a repeated global contract;
- update inbound links and nearest routers when moving files;
- flatten a partition when it no longer reduces ambiguity or discovery cost.

## Top-level home admission

A new direct child of `docs/` should represent a durable knowledge role that cannot fit an existing home without long-term ambiguity in authority, audience, security, retention, lifecycle, or navigation.

Team name, project phase, temporary initiative, tool name, or current roadmap is usually not a semantic role.

## Identifiers

Use the lightest identity that solves the real reference problem:

```text
semantic path             default for ordinary durable knowledge
stable semantic key       optional when rename-resistant cross-document/tool lookup is real
sequential collection ID  append-only ordered decisions such as ADRs
atomic traceability ID    only when an external workflow, control, requirement, or test actually consumes it
```

Examples:

```text
docs/product/order-management.md
key: order-management                 # optional scoped frontmatter
0007-separate-worker-host.md
PAYMENT-RULE-03                        # only with a real traceability consumer
```

Do not assign IDs to every heading or document merely to look governed. Paths and names are sufficient by default.

## Registries and graphs

A registry or graph is conditional. Consider one only when:

```text
multiple repositories or tools need the same machine-readable inventory
README routes repeatedly fail to prevent authority drift
stable IDs already exist and are actively consumed
cross-cutting impact queries cannot be answered from source and links
```

A registry does not become the semantic owner of the entries it indexes.

## Flattening

When the pressure disappears, flatten or merge. Structure is not a one-way maturity ladder.

## Project override

A coherent existing hierarchy may remain deeper or differently named. Preserve it when it materially helps local readers and does not hide authority. Record only significant deviations.
