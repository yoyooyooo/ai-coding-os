# Skill Independence and Retirement

A Skill deserves independent existence only when it owns a distinct semantic problem and changes independently enough to justify its activation and maintenance cost.

## Independence test

Ask:

```text
does it own meaning that no existing Skill owns?
does it change for an independent reason?
can it be routed from a recognizable user or project pressure?
can it fail or be evaluated independently?
would merging it materially confuse authority?
do real tasks benefit from loading it separately?
```

Large content or a different output format is not enough.

## Signs to merge or retire

```text
always co-triggers with another Skill
changes whenever another Skill changes
owns only a template, schema, or tool invocation
repeats the same doctrine with different examples
redirects immediately to another owner
exists to preserve historical naming or release structure
```

## Reference versus Skill

Conditional technical depth belongs in a reference when it does not own a new semantic authority. Examples:

```text
TypeScript projection under application architecture
browser observation under Harness
interface obligations under product definition
Effect deterministic kernel pattern under Effect
```

## Tool versus Skill

A generator, scanner, or deterministic renderer may remain useful while losing Skill identity. Tools perform actions; Skills provide judgment and semantic ownership.

## Retirement safety

Before removing a Skill:

```text
preserve unique semantic knowledge
move useful references to the true owner
update discoverability and descriptions
remove forwarding shells that keep activation cost alive
verify that common tasks still route correctly
```

Do not keep a dead Skill merely for compatibility when no current consumer needs it.
